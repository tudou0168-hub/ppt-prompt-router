# Router Direct Plan Handoff：设计草案

## 状态与范围

本草案只定义 PPT Prompt Router 的下一代 FULL 专业导演交接方式，并以 `government_annual_summary` 为 reference implementation。它不修改 routing 权重、scoring、26 个 Profile、PPT Master 源码、模板兼容、字体或 CI；也不在本轮实现代码。

设计依据：`docs/failure-analysis-3.1.3.md` 证明 B1 的 Plan 语义多数进入了 Stage 2 / SVG，却不足以形成页面级视觉导演；用户提供的《政府年度总结 PPT 语义导演提示词 V15》提供了更自然的导演稿组织方式。

## 1. 目标与非目标

### 目标

- Router 在独立 Director 上下文中完整执行专业提示词，并直接生成 `<project>/analysis/presentation_plan.md`。
- Router 完成该文件后结束，不把 Director Kernel、Profile、Lens 或评分过程继续塞进 PPT Master。
- 新的 PPT Master 上下文从自身 `SKILL.md` 开始，以原生完整流程完成 Route、Stage 1、Stage 2、Design Spec、Spec Lock、Executor、Review 和 Export。
- `presentation_plan.md` 用自然语言说清内容导演与页面级视觉导演意图；PPT Master 保留具体构图、资源实现和 SVG 的自主权。

### 非目标

- Router 不负责 PPT Master Route、模板安装、Design Spec、Spec Lock、Native Shape、SVG、图片实现、Visual Review、PPTX 或 Postflight。
- 不用 Router 代替 PPT Master Strategist / Executor。
- 不新增生产状态机、字段级回执或独立质量门禁。
- 本轮不批量迁移其余 25 个 Profile。

## 2. 新旧流程

### 旧链路（废止为正式主流程）

```text
用户任务 / 材料
  → Router Preflight
  → PPT Master Stage 1
  → 同一主上下文中的 Router Director handoff
  → 当前主智能体写 presentation_plan.md
  → PPT Master Stage 2 / Executor
```

它的问题不只是质量：同一上下文反复加载 Router Kernel、Profile、Lens、Vocabulary 和 Master 角色，会模糊谁在做内容导演、谁在做原生生产，也不能保证 Master 在独立上下文中发挥自身流程。

### 新链路（拟采用）

```text
用户原始任务 + 原始材料 + 明确约束
  → Router 独立 Director Context
  → <project>/analysis/presentation_plan.md
  → Router Context 结束
  → 新的 PPT Master Context（从自身 SKILL.md 开始）
  → Master Route / Stage 1 / Stage 2
  → design_spec.md / spec_lock.md / SVG / Review / PPTX
```

Router 和 PPT Master 的连接是文件交接，不是角色切换或完整上下文交接。

## 3. 上下文隔离与路径边界

### Router 输入

Router 独立上下文只读取：

1. 用户原始请求；
2. 原始材料及其路径；
3. 用户明确的汇报对象、场景、页数、比例、章节、素材限制；
4. 用户明确指定的模板、参考 PPT 或 workspace 路径（只作为用户约束，不读取其内部实现来替代 PPT Master）；
5. Router 的场景选择结果和被选中的专业 Director Profile。

### Router 正式输出

- `<project>/analysis/presentation_plan.md`：正式业务产物；
- 一段短的、可传给新上下文的 PPT Master handoff prompt。

Plan 文件可保留最小文件头 provenance（Router version、Primary Profile、Profile digest），但不写入 Router 的评分、候选、调试日志或完整内部提示词。

### PPT Master 新上下文白名单

新 PPT Master Context 只接收：

1. 用户原始请求；
2. 原始材料路径；
3. `<project>/analysis/presentation_plan.md`；
4. 用户明确指定的模板、参考 PPT 或 workspace 路径；
5. 页数、比例等明确约束；
6. 下文的短 handoff prompt。

不得传入：Director Kernel 全文、Profile 全文、Secondary Lens、Router scoring、Semantic Vocabulary、候选分数、能力地图、Router 内部分析或调试日志。

### 宿主隔离要求

支持 subagent / fresh task / 新会话的宿主，必须真的创建新的 PPT Master Context；安装器和宿主说明需使用各自原生的隔离方式。不得以“请忘记前文”模拟隔离。

### 待 Reviewer 确认：输出项目路径的最小 bootstrap

Router 必须在 Master 之前把文件写到 `<project>/analysis/`，而现有 PPT Master 默认项目初始化通常由其自身流程完成。为避免 Router 接管 Master Route，建议由**宿主**在两个 Context 之外只做路径分配：为本次任务预分配唯一 project path 和 `analysis/` 容器，不选择 Master Route、不写 Design Spec、不安装模板。

新 PPT Master Context 仍从 `SKILL.md` 选择原生 Route；其适配器需把这个预分配路径当作本次任务的目标项目，而不是把 Router 伪装成 Master Stage 1。若用户在 Master Stage 1 对页数、材料范围或核心任务做出实质改变，建议停止当前交接并重新运行 Router 生成同一路径下的更新 plan，而不是让 Master 再造一份平行 plan。

这是路径协作约定，不是生产状态机；本轮只请求 Reviewer 确认方向。

## 4. `presentation_plan.md` 的职责

Plan 是“讲什么、为什么讲、关系是什么、什么最重要、证据应承担什么作用、观众如何感知”的业务导演稿。

它不是 Design Spec、模板选择、几何布局、视觉组件清单或 SVG 说明书。它不规定坐标、百分比、固定图形、固定模板、Native Shape 或 SVG 参数；这些仍由 PPT Master 根据 Stage 1/2、模板、素材与原生能力决定。

现有 `page_role / audience_move / relationship / hierarchy / rhythm_intent / visual_semantics` 可以留在 Router 内部映射或解析层，但不再作为专业 Director 写作的主格式。Director 的正式文字以页面任务、核心观点、内容关系、信息主次、表达意图、页面内容、可用素材和 Speaker Notes 组织。

## 5. `government_annual_summary` 专业提示词结构（草案）

### Role

你是一名长期从事政府机关综合材料、公文写作和领导汇报材料起草的资深笔杆子，擅长把年度、半年和专项工作材料重组为适合政府领导现场汇报的逐页 PPT 语义导演稿。

### Task

完整理解原始材料、用户要求、汇报对象、汇报场景、页数与明确约束。把公文式材料组织为领导可快速形成判断的故事线，并写出每页足够具体、可供 PPT Master 做原生设计的导演意图。所有数据、案例、机制、问题与建议必须来自原始材料；不因视觉需要虚构事实。

### Inputs

- 用户原始请求：`<user_request>`
- 原始材料：`<source_paths>`
- 汇报对象与场景：`<audience_and_context>`
- 页数、比例、章节、模板/参考与素材约束：`<explicit_constraints>`

### Workflow

1. 完整阅读材料，先识别工作主线、阶段判断、代表性抓手、量化成效、机制经验、下一步与需要领导判断的事项。
2. 先形成整套故事，再拆分章节与页面。成效讲清“抓了什么—怎么抓—抓到什么程度—结果—变化”；下一步讲清“目标—重点—抓手—预期成效”；问题建议讲清“现状—影响—工作需求—建议支持”。
3. 每页判断真实内容关系，而不是把“一是、二是、三是”默认翻成卡片。可使用结论—证据、总分支撑、并列、递进、因果、时序、流程、闭环、汇聚、发散、对比、层级等真实关系。
4. 每页明确核心、支撑和补充；把完整口径、过程、案例和现场解释放入 Speaker Notes。
5. 在“表达意图”“信息主次”“可用素材”中完成页面级视觉导演：明确第一视觉主角、退后信息、证据角色、可感知关系、第一眼/第二眼/最后一眼，以及与相邻页不同的节奏体验。不要写坐标、尺寸、固定版式或 SVG 参数。
6. 真实素材优先列出材料中已有的照片、现场图、系统截图、数据截图、案例或可提取数据；没有时明确“无可用事实素材”，而不是泛写“可配图”。

### Final Output

只写入：`<project>/analysis/presentation_plan.md`。

Router 完成该文件后结束 Director 任务，不输出 Design Spec、Spec Lock、SVG 或 PPTX 方案。

## 6. 完整页面导演示例草案

以下示例用于训练 `government_annual_summary` Director 的具体性，格式与最终 plan 相同；它们不规定 PPT Master 的几何构图。

## P03｜两项牵头任务，进度与质量同步达标

### 页面任务
把“完成百分之八十”从单纯进度汇报转化为领导对任务质量和群众获得感的阶段判断。

### 核心观点
两项牵头任务不仅按计划推进，更已在审批提速、便民服务和诉求闭环中形成可验证成效。

### 内容关系
- 主关系：结论—证据
- 关系说明：阶段进度是结论，办理时限、一网通办、免证办和热线闭环共同证明质量。
- 次关系：任务—服务结果

### 信息主次
- 核心：两项牵头任务完成百分之八十，且服务指标达到或超过目标。
- 支撑：重点事项平均办理时限压减至百分之七十一点二四；一网通办百分之九十一点一八；三百余项免证办；一百零三件诉求全部销号。
- 补充：十一项配合任务按牵头部门安排稳步推进。

### 表达意图
- 节奏角色：强化重点
- 第一眼：两项牵头任务完成百分之八十，但不是孤立的进度数字。
- 第二眼：三类服务结果如何证明“进度有质量”。
- 最后应形成的判断：可继续把这两项任务作为下半年攻坚和复制经验的抓手。
- 与相邻页的体验差异：区别于总量数据页，本页让领导看到“任务执行到服务结果”的纵向因果。

### 页面内容
上屏先落阶段判断“80%进度、质量同步达标”，再用改革提速、便民服务、热线闭环三组事实说明成效：办理时限压减、一网通办和免证办、企业诉求全量销号。避免把四个指标作为同权 KPI 平铺。

### 可用素材
原始材料中的任务编号、目标完成进度和服务指标；如材料附件含热线工单或大厅办事数据截图，可作为闭环或服务量的事实证据。当前文本材料未附图片时，明确使用结构化数据而不虚构场景图片。

### Speaker Notes
说明第124、127项的任务来源、目标口径和十一项配合任务的推进情况；解释百分之七十一点二四、百分之九十一点一八和一百零三件的统计范围。

## P05｜企业服务专区，把分散资源组织成全周期服务

### 页面任务
让领导理解专区不是新增窗口，而是把涉企部门、服务动作和增值资源组织为可运行的协同机制。

### 核心观点
企业服务专区以一加三加N服务矩阵，把企业多头跑腿转为全生命周期协同服务。

### 内容关系
- 主关系：机制—成效
- 关系说明：企业需求是服务组织的起点，受理、辅导、帮办、集成服务和四项协同机制共同形成响应能力，运行数据证明其不是概念。
- 次关系：汇聚

### 信息主次
- 核心：从分散审批资源到全周期服务的机制转变。
- 支撑：一窗受理、立体辅导、全程帮办、集成服务；三级协同联动、联审联批、暖心服务、增值服务；六大服务板块。
- 补充：累计服务一千余人次、项目审批一百三十八件、增值服务四百九十六件。

### 表达意图
- 节奏角色：集中承载
- 第一眼：企业全生命周期需求是系统服务的唯一中心，不是多个部门并列展示。
- 第二眼：服务动作怎样汇聚，企业从哪里进入、得到什么响应。
- 最后应形成的判断：专区已经从概念建设转入有运行量的服务机制。
- 与相邻页的体验差异：区别于改革对比页，本页让观众感知“企业需求—协同响应—服务结果”的系统，而不是用圆心向外发散的抽象标签。

### 页面内容
提炼企业需求的典型旅程：受理进入、专业辅导、帮办推进、集成响应，再由协同机制和六类资源托底。上屏保留运行量作为机制已运行的证据，不把所有服务板块平铺成无序清单。

### 可用素材
原文中一加三加N矩阵、四项机制、六大板块和三项运行数据；如有专区现场照片、企业服务专员工作照、联审联批或系统界面截图，应按其事实角色列出。当前文本无附件时，不假设有图。

### Speaker Notes
补充各项机制的责任部门和企业服务场景，解释三项运行数据的时间范围；说明专区与普通窗口的差别。

## P06｜下半年六条工作线，把阶段成效转为全年结果

### 页面任务
把六项工作从并列任务名词重组为实现全年目标的连续推进安排，让领导看到下半年抓什么、先后怎样衔接、预期形成什么结果。

### 核心观点
下半年不是增加任务，而是以六条工作线把上半年形成的改革和服务能力转化为全年结果。

### 内容关系
- 主关系：时序 + 汇聚
- 关系说明：六条工作线各有侧重，但共同承接既有基础并汇聚到全年高质量完成；只在原始材料能够证明时表达依赖和先后，不虚构路径关系。
- 次关系：目标—抓手—预期成效

### 信息主次
- 核心：全年目标与六条工作线共同形成的推进逻辑。
- 支撑：攻坚任务、招商包保、审批改革、专区增值、数字赋能、服务下沉各自的原始材料抓手与预期结果。
- 补充：上一阶段已形成的能力基础和需协调条件。

### 表达意图
- 节奏角色：完成过渡
- 第一眼：全年目标和下半年推进不是一组并列口号。
- 第二眼：每条工作线具体解决什么、依托什么基础、形成什么结果。
- 最后应形成的判断：六条线需同步推进，但领导可据其阶段重点把握支持方向。
- 与相邻页的体验差异：区别于系统机制页，本页强调从阶段基础走向年度结果的时间感和推进感，而不是画一条没有信息含量的波浪线。

### 页面内容
每条工作线必须从原文抽取一个明确抓手和一个预期成效；材料不足时合并或降为 Notes，不能只把六个名词挂在一条线上。上屏围绕“已有基础—下半年行动—全年结果”形成连贯叙述。

### 可用素材
原始材料中的下半年工作部署、已上线事项、项目服务、数字赋能或服务下沉的事实；如无时间表、责任表或项目清单，不伪造甘特图、里程碑日期或责任人。

### Speaker Notes
逐条补充六条线的原文抓手、协同部门、预期成效与需领导指导事项；说明哪些关系是共同推进而非严格前后依赖。

## P07｜两项支撑，保障改革持续落地

### 页面任务
把“缺人、缺运维经费”的资源诉求转化为领导需要判断的服务稳定性与全年任务风险问题。

### 核心观点
队伍专业能力和系统稳定运维，是下半年改革持续落地而非中断的必要保障。

### 内容关系
- 主关系：问题—影响—需求—建议
- 关系说明：人员和运维缺口分别影响服务承接和系统稳定，两项保障共同决定全年任务能否连续推进。
- 次关系：因果

### 信息主次
- 核心：两项保障与全年任务、服务稳定的直接关系。
- 支撑：大厅缺岗人员、专业培训需求、系统稳定运行、安全和运维风险。
- 补充：具体经费测算、岗位数量和处置细节；材料没有的，不补造。

### 表达意图
- 节奏角色：舒展停顿
- 第一眼：需要领导判断的不是一般性保障，而是两项会影响全年交付的关键条件。
- 第二眼：人员和运维各自影响什么，为什么不能相互替代。
- 最后应形成的判断：支持事项应以保障服务规范化和全年任务连续推进为目标。
- 与相邻页的体验差异：区别于行动路径页，本页应形成决策停顿和风险意识，不以两个并列文本框代替因果说明。

### 页面内容
明确写出“当前保障条件—对服务和改革的实际影响—需要协调的支持—支持后保障的结果”。如果原材料没有岗位数量、预算或风险事件，仅陈述已知事实并把补充口径留入 Notes。

### 可用素材
原文中的缺岗、培训、运维和安全运行风险描述；如有大厅排班、系统运维台账、风险清单或服务量变化截图，可作为事实证据。当前没有附件时，不能以装饰性风险图替代证据。

### Speaker Notes
说明保障事项与下半年六条工作线的对应关系，补充能够提供的岗位、培训、运维和风险口径，并给出现场请示的措辞边界。

### 反例：不足以形成视觉导演的写法

> 六项任务向全年目标推进。

这只是语义标签：没有说明六项任务各自的抓手/结果、是否存在真实先后或依赖、领导第一眼要看到什么、哪些信息退后、何处存在证据、为什么它不同于上一页。因此它很容易被实现为“六点一线”或六栏卡片。

## 7. 短 PPT Master handoff prompt（草案）

```text
调用 PPT Master 完成当前 PPT。

原始任务：<user_request>
原始材料：<source_paths>
专业导演稿：<project>/analysis/presentation_plan.md

从 PPT Master 当前 SKILL.md 开始，执行当前版本原生完整流程。

presentation_plan.md 是已经完成的专业内容与页面语义导演结果；原始材料仍是事实权威。PPT Master 自主负责 Route、Stage 1、模板、Strategist、Design Spec、Page Rhythm、Visualization、Native Shape、SVG、图片、Executor、Visual Review、Speaker Notes、Export 和 Postflight。

不要重新执行 PPT Prompt Router，也不要创建第二份平行 presentation plan。如导演稿与用户明确要求或原始事实冲突，以用户要求和事实材料为准。
```

该 prompt 刻意不含 Router Kernel、Profile、Lens、scoring 或能力地图。

## 8. B2 验证办法（只做 P03 / P05 / P06）

### 对照

- A：已有纯 PPT Master 原生版本；
- B1：现有 Router 3.1.3 同上下文 Director handoff 版本；
- B2：Router 独立 Context 直接写 plan → Context 结束 → fresh PPT Master Context 读取白名单并走原生完整流程。

### 固定条件

- 同一审批服务局原始 DOCX；
- 同一 P03、P05、P06 页面范围、16:9 与用户约束；
- 同一可用素材边界；
- 不给 B2 增加 B1 未获得的人工润色、外部图片或虚构数据；
- 记录所用 PPT Master 版本、workspace/template 实际可用状态和渲染字体环境。

### B2 产物

- Router 生成的 `analysis/presentation_plan.md`；
- Master 原生 `design_spec.md`、`spec_lock.md`、SVG、实际渲染 PNG、PPTX、Postflight；
- P03/P05/P06 A/B1/B2 并排 PNG 与一次人工 Contact Sheet 审阅记录。

### 先验问题与判断方法

1. **导演稿是否更具体**：逐页检查是否能读出第一视觉主角、退后信息、真实证据、可感知关系、三段观看顺序和邻页节奏；若只出现“系统、路径、汇聚”等标签，判定未通过。
2. **fresh Master 是否释放原生能力**：检查 Stage 2 是否把自然语言导演结果转为不同的 Layout/Visualization/素材角色，而不是再次只做标题、圆点、线条和同一种蓝底框架。
3. **正增益阈值**：B2 必须在 P03、P05、P06 中至少两页让人工审阅者无需查看 plan 就能更清晰地读出任务—结果、机制—成效、行动—全年结果的关系，并呈现比 A/B1 更有意图区别的跨页体验。否则不推广到完整 8 页或其他 Profile。

## 9. Reviewer 重点确认

1. Router 在 Master Stage 1 前直接生成 plan 的职责边界是否清楚，尤其是 project path bootstrap 是否足够薄；
